# 场景与示例校准

依据竞赛手册第 4 页业务与平台场景、第 5 页场景理解要求和第 8 页展示要求，保留当前应用的学生与职场会议主体，以队友通勤样例补充具体任务。示例输入不等于真实客户案例，产品能力仍需知识库检索证明。

| 业务场景 | 输入入口与任务 | 既有兼容 |
| --- | --- | --- |
| 开学季 | 学生在寝室整理同一份小组汇报、教室展示反馈、图书馆补充引用定稿；重点明确携带与手指触控需求 | campus / student / SC01 |
| 职场办公 | 职场会议会前、会中、会后；明确 Windows、大屏、独立数字键盘；补充地铁通勤与文档、视频会议材料任务 | mobile / meeting / SC02 |
| 内容创作 | 自己拍摄的照片视频、素材挑选、剪辑与交付 | creation，不借用学生模板 |
| 家庭换新 | 家庭文档、照片整理与旧机数据迁移 | family |
| 企业采购 | 办公部署、管理与服务信息核对 | enterprise |
| 门店到访 | 朋友圈一个待核验的核心卖点、体验理由、咨询或到店引导 | store |
| 新品首发 | 核验新品变化、适合人群和选择建议 | launch |
| 节日营销 | 送礼前确认任务；一个卖点与咨询、到店引导 | holiday |

`sceneOptions` 保留已有 id 和 student/meeting 值；新增分类不会被强制映射到 SC01/SC02。`scenario_card.template_id`、既有 fields 和 taskTemplates 保持兼容，增加 `business_scene` 条目，沿用 value/kind/evidence/rationale。业务分类、具体任务和购买阶段是不同维度，选一个分类不能证明任何客户事实。

`role-examples.mjs` 导出原有 `roleExamples`、`buildRoleExample`，并转导出 `business-examples.mjs` 的 `supplementExamples`。补充示例沿用 samples 数据形状，增加 `businessScenario`，可在 ExamplePicker 独立展示；不替代原有组合器，不加入医生或律师示例。

补充示例的完整输入明确声明假设人物、任务、购买阶段和内容目标。一般示例按当前选择的渠道发布；门店到访与节日示例指定朋友圈，并携带 platform 字段供入口同步选择。示例中明确设定的购买阶段可作为该次虚构输入的提取事实；不是现实记录。原学生与会议组合的预算、设备、软件、型号和购买阶段继续保持未知。不得根据身份自动补成准备购买、已经购买或引导咨询。未知目标不会因文本包含“不要补造咨询”而变成咨询目标；有原文依据的咨询或到店目标可提取，不能统一降成互动。目标归纳沿用既有 inference 证据结构，运营者选择沿用 operator。

队友参照包括共享 role-examples、standards 的任务、软件、携带、设备条件等维度，以及 commute-xiaohongshu 示例中的总携带重量、文档、视频会议和兼容待核对思路。未采用队友职业扩展及任何未经本次知识库核验的产品结论。SC01/SC02 读取路径继续以原 student/meeting 模板识别，新增业务字段不修改数据库映射。

第 8 页要求最终优秀运行结果至少三组、覆盖两类业务场景与两个平台；本次新增的是可编辑输入与规则测试，不将静态示例宣称为已经执行的运行结果。朋友圈发布应围绕一个核心卖点和咨询/到店引导，图片采用 1–3 张有来源且型号匹配的图片；公众号和小红书仍按各自渠道规则生成。

验证：`node --test tests/business-examples.test.mjs tests/scenario-card.test.mjs` 覆盖主示例保留、八类业务、未知字段、原文咨询目标与 SC01 研究检索兼容；测试不调用真实 API。另运行 `tests/local-examples.test.mjs`，共 13 项通过。
