# 本地场景卡使用与接入说明

更新日期：2026-10-22。仅本地 8792 服务，未推送线上。

首次生成与核验流程的后续修复见 [首次生成排查](first-generation-reliability.md)。

## 操作方式

打开 http://127.0.0.1:8792/scenario/ 。仍然只需输入一段完整描述；也可点击两张入口卡的按钮填入虚构示例，再按实际情况修改。

- 学生入口：小组汇报，从寝室整理素材，到教室收集反馈，再到图书馆补引用、定稿。
- 职场人士入口：项目会议，从会前准备讨论稿，到会中记结论与负责人，再到会后整理行动项。

点击“仅查看理解”可先看自动整理的场景卡；点击“生成小红书文案”则自动整理并继续原有链路。场景卡本身没有任何需要填写的输入框。“修改原始描述”返回同一段输入，更改后继续生成会重新提取。

结果的“查看研究依据与内容选择理由”中也能查看本轮使用的任务卡。产品沿用自动候选或指定产品，渠道仍为小红书；本轮未实现其他平台。

## 字段和边界

对照参赛手册第 5 页：卡片涵盖人群、任务与场景、主要问题、购买阶段、内容目标、产品及渠道。职业只是入口，不代表所有同职业用户执行同一任务。

| 内容 | 自动处理 |
| --- | --- |
| 职业、具体任务、主要问题 | 从输入提取原话，或保留带原文依据的推断 |
| 地点及任务阶段 | 从任务引用所在原句恢复，不因学生身份自动补造寝室经历 |
| 缺少具体任务 | 可提供明确标为“建议补充”的任务候选，以条件式情境参与写作 |
| 内容目标 | 原文明示时归纳为互动、收藏或咨询；否则默认建议互动；现有运营选择可覆盖 |
| 购买阶段 | 只保留明确原文陈述；未知、假设说明、模型推断均不冒充已确认阶段 |
| 预算、已有设备、软件 | 未提供则未知，不要求填完才能生成，不据职业默认补齐 |

学生明确说考试复习时，不套成小组汇报；医生输入会议任务时，可使用会议任务素材而不把身份改成职场白领。建议补充不修改原始客户输入，不作为产品功能证据。

## 接入位置

- `modules/scenario/shared/scenario-card.mjs`：两类任务模板、摘要生成、来源状态和场景标签恢复；前后端共用。
- `modules/scenario/server/prompt.mjs` 与 `shared/categories.mjs`：新增身份、购买阶段、内容目标提取类别。
- `modules/scenario/src/ExamplePicker.jsx`、`ScenarioCard.jsx`、`scenario-card.css`：两张入口卡及无表单的自动摘要。
- `src/handoff.mjs`：服务端从已校验理解重新构建卡片，放入 `customer_context.scenario_card`；不接受前端伪造的卡片事实。
- `src/research-context.mjs`：卡片进入 `content_brief.scenario_card`，与研究素材一起传给生成及润色；产品事实仍来自本型号原文。
- `prompts/system.txt`：建议仅作条件式场景，不能升级为客户事实或产品能力。

## 验证

147 项自动测试通过；构建通过。浏览器验证两张入口、没有新增表单、自动摘要、生成与失败定位、输入保留、复制导出和手机布局。学生场景完成真实生成与辅助核验；保存结果的卡片地点标签随后依据同一份已提取原文作确定性重建，正文与核验记录没有改写。会议场景验证中发生过一次模型网络错误和一次购买阶段字段误分类；网络失败保留诊断编号，误分类已由回归测试覆盖并修复。

最终会议场景也通过真实的输入理解、卡片构建、生成、辅助核验、图片加载、复制导出与手机布局检查。两张卡片均已进入实际生成所用的研究上下文，购买阶段为未知。

该提取及文案核验仍依赖模型，不能理解为任意输入保证正确。遇到真实相互冲突的条件仍需澄清；普通未知信息不阻止先生成草稿。
