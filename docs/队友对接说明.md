# 输入卡与输出结果对接说明

适用范围：当前已跑通的「输入任务 → ima 产品资料与图片 → DeepSeek → 结构校验 → 页面展示 / JSON 导出」最小链路。本文描述代码现状和协作约定，不替代比赛要求。

三人的分工合理：一人把输入信息定义清楚，一人把生成结果定义清楚，一人负责接口与整条链路。**先保留现有字段名，把格式和样例交齐，再逐步提高内容质量。**

本文文件路径均相对于项目根目录。两位队友修改各自负责的文件，交回文件和变更说明即可，不需要自行接 ima 或 DeepSeek。

## 1. 谁交什么

| 负责人 | 必交文件 | 交付内容 |
|---|---|---|
| 输入卡同学 | `contracts/input.schema.json`、`examples/task.json` | 字段定义、必填规则、选项、默认值，以及一份能直接运行的输入 JSON |
| 输出结果同学 | `contracts/output.schema.json`、`prompts/system.txt`、新增 `examples/expected-output.json` | 输出结构、各部分写作要求，以及一份手写的理想输出 JSON |
| 链路集成同学 | 按需修改 `src/`、`server.mjs`、`public/index.html`、`tests/` | 合并契约、处理复杂控件或结构变化、运行验证、调整展示 |

输入卡同学建议再交两份不同客户 / 平台的输入，放在新增的 `examples/input/` 目录。输出同学的手写样例是设计目标，须标明对应输入与示例来源，不能当成真实运行结果。

文件统一用 UTF-8。JSON 不允许注释和末尾多余逗号；字段名用英文，字段内容可以用中文。不要在文件中加入账号、API Key 或签名素材链接。

## 2. 输入卡同学：定义表单，交一份真实任务

### 修改位置与格式

编辑 [`contracts/input.schema.json`](../contracts/input.schema.json)，它定义「有哪些字段」；编辑 [`examples/task.json`](../examples/task.json)，它定义「这一单具体填了什么」。两者不能混为同一种文件。

当前字段约定：

| 字段名 | 类型 | 必填 | 填写要求 |
|---|---|---|---|
| `product` | string | 是 | 知识库中的完整型号，区分鸿蒙 / Windows 和配置；当前不能仅填“轻薄本”让系统自动选型 |
| `audience` | string | 是 | 客户是谁，身份及已知背景 |
| `scenario` | string | 是 | 具体任务、发生场景、当前困扰与顾虑 |
| `platform` | string | 是 | 当前四选一：小红书、公众号、朋友圈、门店海报 |
| `goal` | string | 否 | 本次希望推动的行动，例如咨询、到店体验 |
| `notes` | string | 否 | 补充事实、限制、未知信息 |

可直接运行的输入样例：

```json
{
  "product": "HUAWEI MateBook 14（鸿蒙版）",
  "audience": "准备购买第一台电脑的大学新生",
  "scenario": "每天带电脑上课，整理课堂笔记和小组作业；担心常用软件兼容性，希望先到店体验。",
  "platform": "小红书",
  "goal": "引导咨询和到店体验",
  "notes": "先验证链路，暂不报价；未知信息明确标注。"
}
```

### 哪些修改会自动生效

在 `properties` 中新增**平铺的字符串字段**即可接入。比如增加预算，可新增以下属性；这是 schema 片段，不是任务输入：

```json
{
  "budget": {
    "type": "string",
    "title": "预算范围",
    "description": "客户口述的预算；不清楚时留空",
    "maxLength": 120,
    "default": ""
  }
}
```

实际任务中相应填写 `"budget": "6000—8000元"`。建议第一轮新增字段先设为可选，避免旧样例全部失效。

页面目前这样使用 schema：

- `title` 是表单标签；`properties` 的顺序决定输入字段顺序。
- 有 `enum` 就显示下拉框；没有 `enum` 时，`maxLength > 500` 显示多行文本框，其余显示单行输入框。
- `default` 是初始值；`required` 定义必填字段。
- `description` 可以说明字段含义，但目前不会作为页面帮助文字展示。
- 表单提交的值都是字符串。新增字段会传给模型，但检索仍主要依据 `product`；新增“预算”不会自动实现报价或选型。

需要集成人员同步处理的变更：改动原四个必填字段的名称；新增必填项；引入数字、布尔、多选、数组、嵌套对象；需要条件显隐或自动追问。新增必填项时必须一起更新输入样例和测试数据。

当前缺少必填信息会提示错误，不会自动开启多轮问答。对于可选信息，说明空值代表“未知”还是“不适用”，不要用默认值冒充客户已确认的事实。

### 输入卡交付清单

- [ ] schema 与输入样例的字段名、类型、枚举一致。
- [ ] 每个新增字段说明业务含义、是否必填、未知时如何处理。
- [ ] 至少一份样例使用当前知识库已有的完整型号。
- [ ] 告知输出同学新增字段如何影响内容，例如预算影响推荐表述、顾虑影响演示与跟进。
- [ ] 若扩展平台枚举，同步让输出同学补充该平台的写作规则。

## 3. 输出结果同学：定义结果结构与写作规则

### 三个文件各自负责什么

1. [`contracts/output.schema.json`](../contracts/output.schema.json)：约定模型返回哪些字段、各字段类型与必填规则；页面也用其中的 `title` 显示标题。
2. [`prompts/system.txt`](../prompts/system.txt)：规定各字段怎么写，例如客户判断要有依据、不同平台的表达、演示步骤、跟进内容。
3. 新增 `examples/expected-output.json`：手写一份理想结果，帮助大家对齐质量。**它只作为样例，不会被程序自动读取成提示词或替代模型输出。**

当前输出必须包含以下八个字段：

| 字段 | 类型 | 内容要求 |
|---|---|---|
| `customer_insight` | string | 客户任务、顾虑与依据，区分已知信息和推测 |
| `strategy` | string | 为什么选这个场景、卖点和平台表达 |
| `content` | object | 固定包含字符串 `title`、`body`、`call_to_action` |
| `image_plan` | array | 每项包含字符串 `source_ref`、`position`、`caption`；无图时可为空 |
| `sales_plan` | object | 字符串 `quote` 和 `demo_script`；当前报价待规则，演示约3分钟 |
| `follow_up` | array | 每项包含整数 `day` 和字符串 `message`；按第1、3、7天提供差异化话术 |
| `source_refs` | array | 使用的来源编号字符串列表，至少一项 |
| `pending_confirmation` | array | 待确认事项字符串列表；没有时为空数组 |

下面是**结构演示，不是产品事实或真实生成记录**。仅假定配套示例资料提供了文本 `S1` 和图片 `I1`；实际交付的理想输出应配套说明它使用的资料。正文有意缩短，正式写作按 prompt 的要求完善。

```json
{
  "customer_insight": "已知：客户是大学新生，需要带电脑上课，担心软件兼容。待确认：专业、常用软件和预算。",
  "strategy": "从第一台电脑的选购顾虑切入，邀请客户带常用任务到店核验；小红书采用短段落。",
  "content": {
    "title": "第一台电脑，先带上你的常用任务来试试",
    "body": "先列出上课和小组作业常用的软件、文档与操作，再到店逐项体验。产品介绍以本次提供的资料为依据[S1]，尚未核实的兼容性先确认。",
    "call_to_action": "把专业和常用软件告诉我们，一起准备到店体验清单。"
  },
  "image_plan": [
    { "source_ref": "I1", "position": "首图", "caption": "使用本次资料提供的产品图，具体画面需人工确认。" }
  ],
  "sales_plan": {
    "quote": "待提供价格与优惠叠加规则，暂不报价。",
    "demo_script": "0—30秒：确认专业和常用任务；30—120秒：在得到客户同意且具备所需软件和样例文件后试用，缺少条件则记录待验证项；120—180秒：共同记录结果、未解决顾虑和下一步。"
  },
  "follow_up": [
    { "day": 1, "message": "方便发一下你常用的软件名称吗？我们先准备体验清单。" },
    { "day": 3, "message": "之前担心的兼容问题还有哪些没确认？可以约时间到店逐项体验。" },
    { "day": 7, "message": "选购计划有变化吗？如果仍有未确认的任务，我们可以继续核对。" }
  ],
  "source_refs": ["S1", "I1"],
  "pending_confirmation": ["专业与软件版本", "预算", "优惠规则", "配图内容是否适合本次场景"]
}
```

### 引用与结构约定

- 产品事实来自本次传入的资料；引用写成 `[S1]`，图片选择使用 `I1` 等编号。编号由每次检索分配，不能假定 `S1` 永远是产品事实文件。
- `source_refs` 要收齐文中所有 `[S…]` / `[I…]` 引用，建议同时收齐配图引用。`image_plan[].source_ref` 必须对应本次实际返回的图片；无图时不能编造 `I1`。
- 保留 `content.title/body/call_to_action`、`source_refs`、`image_plan[].source_ref` 的名称和类型。文案复制、来源校验直接使用这些字段。
- 其他区块可以扩充，但字段类型变化需要同步给集成人员，更新测试数据和旧结果兼容处理。例如把客户洞察从字符串改成五维对象，需要同时修改 schema、prompt、样例。
- 第一轮若仅想细化客户洞察，可先在字符串中分项表达；需要固定五维结构时再一起确定字段，维度名称以赛题材料为依据。
- 模型必须只返回一个 JSON 对象，不能包 Markdown 代码围栏。字段内部换行使用 JSON 的 `\n`。
- 保留现有 prompt 中的来源约束、型号区分、未知信息待确认和不虚构优惠 / 兼容性的要求。

### 展示与校验的实际边界

页面支持通用的对象、数组和文字展示，**文字不会按 Markdown 渲染**。想要时间轴、特殊洞察卡、报价表或固定区块顺序，需要集成人员修改 `public/index.html`。只调整 schema 中字段顺序不能保证输出卡片顺序。

`image_plan.position` 目前是配图建议，图片展示在来源区域，不会自动嵌入文案指定位置。复制按钮只复制 `content` 的标题、正文和行动引导。

校验器只支持本项目使用的 `type`、`properties`、`required`、`enum`、`maxLength`、`items`、`minItems`。`description` 不是硬校验；`pattern`、`oneOf`、数值上下限等暂未实现。第1、3、7天各出现一次、正文约300字、脚本约3分钟目前主要靠 prompt 和人工检查，不能把写进说明当作代码已强制校验。

报价计算、自动发送跟进、逐句事实核验均未实现。输出同学可以定义未来需要的数据格式，由集成人员补对应功能；本轮不要通过生成文本宣称这些能力已接通。

### 输出同学交付清单

- [ ] schema、prompt、理想输出样例使用同一套字段和类型。
- [ ] 样例覆盖全部八个区块，并说明对应的输入与来源。
- [ ] 明确客户洞察、平台内容、演示和跟进分别怎样才算可用。
- [ ] 无资料、无图片、价格规则缺失时有合理的空值 / 待确认表达。
- [ ] 单独列出需要前端支持的展示需求，避免只改 prompt 后误以为页面会自动实现。

## 4. 做好后如何接入现有链路

### 交接方式

两位队友分别交回自己的文件，并附三行说明：

```text
本次修改：新增 / 删除 / 改名了哪些字段，表达要求如何变化。
样例对应：输入文件、期望输出文件、使用的示例资料。
需要集成：是否涉及新增必填项、类型变化、复杂控件或特殊展示。
```

最小协作顺序：输入同学先发字段表 → 输出同学明确如何使用这些字段 → 两人分别完善文件 → 集成人员合并并跑一次真实任务。不要等各自全部做完才核对字段名。

### 合并与运行

1. 集成人员将交付文件放回对应路径；新样例可以另存，避免互相覆盖。
2. 若有字段改名、类型变化或新增必填项，先修改依赖代码和测试数据。
3. 在项目根目录执行本地测试：

```powershell
npm test
```

4. 服务已运行时直接打开 `http://127.0.0.1:8787/` 并刷新页面。schema 改动刷新后重新载入；prompt 改动在下一次生成时读取，无需重启。改运行代码或环境变量时重启服务；服务未运行时用 `npm start` 启动。
5. 填入新样例，点击生成，检查输入、检索、生成、展示和导出。也可以用 CLI 做真实联调：

```powershell
node cli.mjs run --input examples/task.json --output output/handoff-check.json
```

真实联调需要本机有效的 ima / DeepSeek 配置并调用模型；本地测试不调用付费模型。修改文件后要重新生成，“上次结果”只是已保存结果，不会按新 prompt 自动重写。

队友电脑上的 `127.0.0.1` 指向他们自己的电脑，不能借此访问你的服务。可由你统一做联调；队友若单独运行，需要拿到项目并配置自己的本地凭证，不把密钥写进交付文件。

### 结果怎么判断

- 输入字段正常出现，必填、选项和长度校验符合预期。
- ima 找到指定型号，有原文进入模型；新增输入能反映到对应输出中。
- 所有输出区块符合新格式，正文引用存在，配图引用确实是图片。
- 客户信息不足时标明待确认；报价规则缺失时不编造价格。
- 跟进覆盖第1、3、7天，演示包含具体行动和检查点；这些内容仍需人工阅读。
- 页面展示、复制文案、下载 JSON 均可用。本地测试通过只说明已有测试覆盖的行为成立，不能替代真实联调。

## 5. 输出样例与下载文件不是同一层结构

输出同学负责的 `expected-output.json` 是模型结果本体，即 `customer_insight`、`content` 等八个字段所在的对象。

实际下载 / CLI 保存的文件由程序再包一层，包含 `schema_version`、`input`、`output`、`sources`、`checks`、`meta`。输出同学的对象放在其中的 `output` 字段；**不要让模型生成外层来源、校验状态或运行时间**。

`sources` 由 ima 检索产生，`checks` 目前只表明结构和来源编号检查结果，不代表语义或完整营销合规审核通过。图片另存在 `output/media/`，下载 JSON 不会把图片文件嵌入进去。

集成人员如需对接其他前端：`POST /api/run` 的请求体是输入任务 JSON，响应为逐行 JSON 流，事件类型包括 `progress`、`result` 和 `error`；成功数据在 `result` 事件的 `result` 字段。运行中失败也可能发生在 HTTP 200 之后，应以最终事件判断结果。
