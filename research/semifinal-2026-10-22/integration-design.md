# 复赛研究资料如何接入当前软件

日期：2026-10-22。状态：研究资料与接入设计，尚未替换线上生成流程。

更新：学生、职场会议两类小红书流程已在本地接入研究检索、独立润色与知识库辅助核验。本文仍保留后续设计，朋友圈、销售跟进等不属于本轮实现范围；实际验证记录以 [本地验证说明](../../docs/local-semifinal-verification.md) 为准。线上未变更。

## 已确认的方向

- 本地资料包替代 ima 已获允许，保留来源与版本即可，不再列为验收阻塞。
- 消费群体先研究华为 PC 实际购买者；数据不足时用中国笔记本/轻薄本研究作明确标注的替代依据。
- 先完善小红书，通过研究选择两类业务场景，再针对朋友圈调整结构、图片与行动引导。
- 产品分类增加“功能支撑的任务、可表达范围、证据不足不能承诺的内容”。
- 追问机制后置，只考虑会改变产品、卖点或下一步的必要问题。
- 预设店员问题和动作库，按本轮明确需求选择；不把候选顾虑写成客户真实顾虑。

## 先定义四类资料的用途

| 资料 | 可支持的判断 | 不可用于证明 |
|---|---|---|
| 产品资料 | 完整型号、配置、功能、价格条件、图片归属 | 客户已经拥有设备、所有应用都兼容 |
| 群体与情境研究 | 候选业务场景、触发原因、内容切入点 | 这个具体客户的职业、预算、动机已经确定 |
| 营销案例与表达模式 | 标题、开头、图文顺序、互动形式 | 华为 PC 的功能和预期销量、未经验证的爆款效果 |
| 店员操作指南 | 遇到具体问题时可做什么、用什么验证 | 问题已经发生、客户已经同意跟进、操作已执行 |

这四类 JSON 保存为可审阅源文件，build_database.py 汇总为 SQLite 的 datasets、sources、records、record_sources 表。数据库查询只是资料定位，不自动升级记录的真实性；正式成稿仍读取本轮完整型号的原文。

## 页面怎么变化

1. 保留完整需求输入。已有真实描述优先，不要求使用者必须点卡。
2. 将身份卡与任务卡分开：身份可选；任务是核心，如素材整理、公开资料阅读、会议材料编写。任务候选可以按身份排序，但不因此变成客户事实。
3. 地点作为任务下的可选情境。跨地点用同一件产物串联，而不是强迫每篇文章填满三个地点。
4. 增加一个运营选择“这篇内容希望带来什么”，如话题互动、咨询或体验。必须记为 operator_selected 或 default_suggestion，不能记为客户购买阶段。
5. 理解区显示已知、未知、研究启发。研究启发默认折叠，保留选择或替换入口。
6. 产品保持“指定产品”和“按需求推荐”。前者支持比赛指定产品；后者先排除明确不满足的硬条件，再显示有依据的候选和缺口。
7. 成果区仍以完整小红书文案和同型号图片为主。店员下一步作为独立辅助区域，不能混入广告正文；未触发的指南不显示。

现有位置：modules/scenario/src/ExamplePicker.jsx、shared/role-examples.mjs、src/main.jsx、src/Handoff.jsx、src/ResultView.jsx。当前三类身份只是人工示例，新人群选择以研究结果为准，不因旧示例存在而保留为销量排名。

## 生成链路需要怎样接入

完整输入 → 观察提取 → 场景/营销目标选择 → 产品原文检索 + 情境资料检索 + 写作模式检索 → 文案生成 → 主张核验 → 改写及再次核验 → 完整文案与可展开依据。

建议保持证据分区：

```json
{
  "customer_context": {"facts": [], "unknowns": [], "inferences": []},
  "content_brief": {"goal": "conversation", "goal_origin": "operator_selected", "buying_stage": "unknown"},
  "product_evidence": [],
  "research_context": [{"record_id": "某条研究记录", "usage": "candidate_angle", "is_customer_fact": false}],
  "writing_patterns": [],
  "sales_guidance_candidates": []
}
```

标识符示意不代表这些字段已经进入运行接口。research_context 中的购买阶段若无客户证据，只能供写作选择候选情境，不得覆盖 unknown。不要默认用户“想买电脑”“已到比较阶段”或“预算紧张”。

### 当前已发现的具体接入问题

- src/handoff.mjs 的 goal 默认值是“引导咨询和到店体验”。
- src/deepseek.mjs 的小红书写作要求将 CTA 固定为自然互动，排除了到店邀请。
- prompts/xiaohongshu.txt 同样偏向评论互动。

接入时需统一内容目标的来源与优先级：明确运营目标 > 系统候选目标。未知购买阶段继续为 unknown。CTA 可以随目标改变，但店址、活动、优惠、预约能力必须来自输入或资料，不得为完成目标而编造。

## 知识库复核的最小可实施版本

将每条可验证的产品主张提取为：原句位置、完整产品及配置、主张类型、引用来源、必要条件。逐条返回 supported / qualified / unsupported / contradicted / unverified。

- 参数与价格：先用确定性检查对照单位、数值、配置和时效；不同价格口径不相减。
- 功能：检查动作、方向、设备与软件范围；“触控”不能自动支持“某软件能批注”。
- 跨产品比较：两边需完整型号、同口径资料；否则不输出优劣结论。
- unsupported / contradicted：删除或用有据的更窄主张改写；不只是补一个来源编号。
- qualified：正文保留改变主张含义的短限定，详细条件进入展开区。
- unverified：不得标为通过；可换用有依据的能力或保留为未交付诊断。
- 改写后的最终文本再次核验；设有限重试，持续失败返回明确缺口，不能循环调用无上限。

生成模型自审只能辅助，状态不能直接命名“全部事实真实”。当前 pipeline 只检查编号/结构，不能在功能实现前修改完成声明。

相关位置：src/pipeline.mjs、src/deepseek.mjs、contracts/output.schema.json。新增审阅结果建议放在外层 checks 和 review_trace，而不是破坏当前六字段成稿契约。

## 店员指南的触发原则

优先显示本轮明确未解决的一至两项问题；仅职业匹配不足以触发软件、预算或隐私顾虑。未明确需求时显示“可进一步了解”，不得写成“客户担心”。每项由确认问题、下一步动作、所需证据、完成条件组成；本轮不规定强制 1/3/7 天，不自动发消息。

## 后续接入验收用例

| 输入或干扰 | 预期 |
|---|---|
| 指定产品但没有职业 | 使用已知任务；不强迫自动换型或默认为学生 |
| 只说学生，未说明设备 | 可选任务卡；不宣称已有华为手机 |
| 同一职业分别做素材创作与专业开发 | 任务卡、候选、证据与文案切入点有实质变化 |
| 必须 Windows，手动选鸿蒙版 | 后端继续拦截系统冲突 |
| 研究说某群体重价格，客户没说预算 | 不把价格敏感写入客户事实 |
| 只有触控原文，却生成任意软件批注承诺 | 复核判为证据不足并改写，不能仅因 S 编号存在通过 |
| 图片型号正确但与任务不相关 | 保留型号检查，同时调整排序；不凭画面证明软件功能 |
| 目标为评论互动，购买阶段未知 | 结尾可用任务话题，不自造到店预约或折扣 |
| 明确要求咨询，但没有门店联系方式 | 形成合适咨询引导，不编造地址或预约链接 |
| 同一任务转朋友圈 | 保留事实，缩为一个核心任务和卖点，调整图片与引导，不机械截短 |

## 本轮完成与后续实现的分界

本轮完成研究源文件、来源登记、可查询数据库和接入设计。网页卡片、生成时自动检索、逐句语义复核、朋友圈与店员辅助区域属于后续代码实现，不能因研究数据库已存在而宣称这些功能已经上线。
